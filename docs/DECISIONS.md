# Decisions

Settled decisions and why, newest ids last. Ids are `W-nnn`; `D-nnn` refers to the Tamale repo's register.
"Proposed" means the planning agent recommended it on 2026-10-08 and the owner has not yet confirmed it.
"Owner" means the owner asked for it. Don't relitigate a confirmed decision; if one looks wrong, say so and ask.

| Id | Decision | Why | Standing |
|---|---|---|---|
| W-001 | A scheduled pipeline, not an always-on agent | Cheaper and auditable; a model is used only to read letters and write summaries | Proposed |
| W-002 | Public data only, in its own project and repo; firm-side consumers are built in the Tamale repo | The ingest job fetches untrusted content from the internet, so it must not sit beside Tamale or APX credentials. A deliberate exception to D-045 (one repo and image for Tamale workloads) | Proposed |
| W-003 | Postgres is the system of record; Tamale is an output | Tamale is a notes system, not a query engine; overlap and change questions need SQL | Proposed (owner suggested storing in Tamale; summaries still go there) |
| W-004 | Where database `whales` lives: a second database on `pg-tocqv-context`, or its own small server | Sharing avoids a second server, which counts only as a switching cost (D-151). The Tamale read of 2026-10-08 favours a separate server: `pg-tocqv-context` has a public endpoint open to all Azure services, one Entra admin, and its role script never revokes CONNECT on `context` from PUBLIC (live server not checked), so any new login role (a `whales_ingest` role included) could connect to the confidential database until Tamale's server is changed | **OPEN: owner to choose.** Recommended: own server |
| W-005 | Consumers read only the `api` views | Internal tables can change without breaking the Research Assistant | Proposed |
| W-006 | 13F first; letters and 13D/G later | 13Fs are structured, free and enough to test whether the signal is useful | Proposed |
| W-007 | Track forward performance from each event: first mention or initiation, adds, full exits | A rough check of whether following a manager or a signal is worth anything | Owner |
| W-008 | Two clocks per event: quarter-end and filing date | Quarter-end approximates the manager's result; the filing date is what a follower could capture | Proposed |
| W-009 | An "add" needs a threshold (20% share increase, split-adjusted, to start) | Share counts move for trivial reasons | Proposed |
| W-010 | Leave out multi-strategy and quant shops (Citadel, Millennium, Point72, Renaissance) | Thousands of positions and high turnover swamp the overlap signal | Proposed |
| W-011 | Whale data is a further source for the Research Assistant, through its front door and fixed query specs, not free-form SQL | Matches that project's spec-driven query model (D-001); easier to cite and to stamp with `as_of` | Owner asked for the source; the mechanism is proposed |
| W-012 | Joins to APX holdings happen in the Research Assistant, never here | APX positions are firm-confidential; this database is public data | Proposed |
| W-013 | Tamale notes: coverage and held names only, one "Whale activity" note per company per quarter, updated in place, labelled as delayed public data, written by a service account, dry run first | Keeps Tamale from being flooded and keeps machine output identifiable | Proposed |
| W-014 | LP-received letters are excluded by default | Confidentiality terms, fiduciary and misappropriation risk; needs fund-by-fund compliance clearance | Proposed |
| W-015 | For letters, store summaries, short quotes and a link, not full text for redistribution | Copyright | Proposed |
| W-016 | Project docs follow the Tamale repo's convention: `AGENTS.md` authoritative, `CLAUDE.md` imports it, `docs/STATUS.md`, `DECISIONS.md`, `HANDOFF.md` | One convention across the owner's projects; platform-neutral for any agent | Proposed |
| W-017 | Topic analysis with two lenses: what managers say (letters) and what they own (13F holdings mapped to topic baskets) | The owner asked for a topic analyzer. Letters carry the views; holdings show whether positioning matches, and the holdings lens works before any letters are ingested | Owner asked for topics; the two-lens design is proposed |
| W-018 | A controlled topic list in `config/topics.yaml`; the model may only tag topics on the list, and new ones wait in a candidate queue for a person to approve | Free tagging produces dozens of near-duplicates ("rates", "Fed policy", "yields") and trends that cannot be compared across quarters; matches the context layer's ratify-before-tagging rule | Proposed. **Conflicts** with D-026 and D-109: Tamale sources its ~250 Topic entities live and never owns a copy (`tamale/ops/topics.py`), but this project cannot read Tamale (W-002). Owner to choose the source of truth (STATUS.md) |
| W-019 | Every topic stance shown to a user carries the quote and a link to the source | Stance classification is a judgment call by a model; the reader must be able to check it | Proposed |
| W-020 | The ingest job runs as its own image, under its own user-assigned managed identity, in a Container Apps environment that does not mount the Tamale `weeklystate` share; never under `id-weekly-job` | `id-weekly-job` holds Key Vault Secrets User on all of `kv-tocqv-research`, and `weeklystate` (firm data) is linked at the `cae-research-automation` environment level. Either would break W-002 | Proposed |
| W-021 | Reporting to the Tamale fleet goes through D-052 (an external job): a `runner=external` row in Tamale's `reference/automation_jobs.csv` and a Storage Table Data Contributor role scoped to the `AutomationRuns` table only. No immediate failure email; the watchdog's stale flag is the alert | The fleet runner's preflight needs Tamale and Microsoft 365; the account-wide role would also expose the Research Assistant's audit tables and the `AutomationChanges` undo log; the alert email needs the Graph secret | Proposed; the table-scoped grant is not yet proven |
| W-022 | Tooling copies the Tamale repo: Python 3.13, setuptools, pip-tools `pip-compile --generate-hashes` locks (runtime and dev), Ruff (line length 110, rules E/W/F/I/UP/B), pytest with a `live` marker excluded by default, plain numbered SQL migrations with a small `migrate()` and a migrations table (no ORM, no Alembic), CI actions pinned to commit SHAs | One convention across the owner's projects (D-047, D-093). Unlike the Tamale CI, `setuptools` and `pip-audit` get pinned too | Proposed |
| W-023 | Build this project's own EDGAR and OpenFIGI clients | Nothing exists to share: the Tamale EDGAR resolver is designed but unwritten, and its OpenFIGI client sends only ticker plus exchange and imports Tamale code. Revisit once both exist | Proposed |
| W-024 | A manager is a set of filer CIKs, each with the quarters it counts for (`core.filer`). A manager's quarter is the union of its filers' 13F-HR lines. Duplicate filings are excluded by listing them in config. If two of one manager's filers report the same entry count and value total for a quarter, the ingest stops and asks | The 2026-10-08 survey found successions (Greenlight to DME, JANA LLC to JANA Management, Pershing Square Capital Management to Pershing Square Inc.), parallel books (Fundsmith) and one identical double filing (Situational Awareness 2026 Q1). See `docs/MANAGER_SURVEY.md` | Proposed |
| W-025 | Detect 13F value units for each filing, never by filing date alone. For each share line, implied price is value divided by shares; compare it with the median for the same CUSIP and quarter across all filers in the SEC bulk data set. Near 1/1000 of that median means the filing is in thousands; ambiguous means refuse and flag | Baupost and Duquesne still report in thousands in 2026, and the summary-page reconciliation cannot catch it | Proposed |
| W-026 | Ingest every verified candidate (30 managers, about 32 filers), tagged by style cohort (technology and growth; value and quality; activist; macro and credit), and run overlap reports within and across cohorts rather than limiting the watchlist to 20. Leave Whitebox out (W-010) | 13F volume is tiny, so a smaller list saves almost nothing. The noise risk is in mixing styles, which cohorts handle | Proposed; owner to confirm |
